# 게시·조회 사용량 제어

검증 기준: 2026-10-25. 대상: YKH 팀 `ykh1/jc-live`. 이번 변경은 로컬 소스이며 운영 적용 전 상태.

실제 제455회 방송량을 반영한 후속 계산은 [제455회 사용량 재산정](SESSION455-USAGE.md) 참조. 아래 176시간은 용량 검산 가정이며 확인된 방송량이 아님. 제455회 다시보기 50건의 영상 합계는 약 129.7채널·시간, 겹치는 방송 시간을 반영한 사이트 시간은 약 45.7시간으로 추정. 목표 접속자 300명과 평균 동시 접속자 300명도 구분 필요.

## 현재 구조와 변경

| 구간 | 변경 전 | 변경 후 |
|---|---|---|

| 장애 | 다음 주기 재시도 | 영속 요청 ID, 백오프, 최대 시도, 원인별 차단 |

## 데이터·버전·보안 계약

- 공개 해시: `publicUpdate` 검증을 거친 표현을 키 정렬 후 SHA-256 계산. 전송 시각·요청 식별자 제외, 의미 있는 전사 배열 순서 유지. 공개 게시 단계 자체의 상태 변화로 재전송이 발생하지 않도록 정규화.
- 실시간 `whisper-draft-v1` 초안과 후보정 교체 유지. 과거 이력·회의록의 `ai-corrected-v1` 검증 유지. 관리자 키, DB, 녹음, 비공개 후보·프롬프트는 공개 대상에서 제외.
- 한 게시 요청의 `publisher_id`, `revision`, `request_id`, `content_hash`, `published_ms`를 전송 전에 SQLite에 저장. 재시도 시 `sent_ms`만 갱신. 응답 유실·수동 재개 후에도 이미 시도한 요청 ID 유지.
- 서버는 같은 ID·버전·해시·게시 시각의 재전송을 중복으로 승인. 새 요청은 전송 시각 허용 범위와 버전·게시 시각 역행 검사. 기존 객체는 ifMatch, 최초 객체는 덮어쓰기 금지. 쓰기 결과가 불명확해도 무조건 덮어쓰기 금지.
- 기존 성공 목록을 DB에서 다시 읽어 다른 인스턴스가 승인받은 회의록 목록 보존. 동일 DB 게시자는 30초 임대와 요청 ID 대조 적용. HTTP 타임아웃은 25초.
- 서로 다른 PC의 전역 소유권 고정에는 서버 `JC_PUBLISHER_ID` 설정 필요. 미설정 시 기존 객체별 소유권만 보호되며 새 경로의 다른 게시자를 차단하지 못함. 설정 변경은 이번에 미실시. 복제 DB를 두 PC에서 동시에 게시하는 운영 금지.
- 새 형식으로 갱신된 객체는 구형 게시자의 쓰기를 409로 거부. 코드 롤백과 게시 프로토콜 롤백을 구분.

## 기본 제어값

| 설정 | 기본값·범위 |
|---|---|
| `interval_ms` | 60,000. 로컬 정기 점검 간격이며 무조건 전송 주기가 아님 |
| `minutes_interval_ms` | 300,000. 진행 중 회의록 갱신 제한, 첫 생성·상태 변경·큰 구간 증가는 기존 우선 처리 유지 |
| `min_snapshot_ms` | 1,000. 허용 범위 1,000~5,000 |
| `burst_limit` / `burst_window_ms` | 모든 게시 합계 128회/60초. 각 범위 3~600회, 1,000~60,000ms |
| `retry_limit` | 논리 요청당 최대 5회, 1~10회 설정 가능 |
| `retry_base_ms` / `retry_max_ms` | 1,000 / 60,000. 지수 백오프와 0.5~1.5배 지터, Retry-After 우선 |
| SDK 재시도 | 런타임 내부 기본 0회. `VERCEL_BLOB_RETRIES` 명시값은 정수 0~2만 허용, multipart 비활성 |

429·일시 오류는 상한까지 재시도. 인증·한도·저장소 중지·충돌·잘못된 본문·크기 초과는 즉시 차단. 플랫폼 402는 서비스 중지 범주로 차단하되 정확한 결제·한도 원인은 관리 화면에서 확인. 강제 전송·종료 flush도 차단 해제 불가. 로컬 수집·원문 저장·후보정은 독립적으로 지속.

대기 snapshot은 아직 전송하지 않은 동안 최신 상태로 합침. 이미 시도한 항목은 중복 확인 후 다음 최신 상태 게시. 전체 기록은 SQLite·회의록에 보존. 원격 차단 중 공개 화면은 마지막 승인본에 머무르며 자동으로 최신 상태라고 표시하지 않음. 운영자가 원인을 해결한 뒤 명시적으로 재개.

선택적 `budget`: `period_id`, `advanced_limit`, `advanced_used`, `reserved_final`, `enforce` 지정. 기본은 예산 미설정이며 설정해도 `enforce`가 true일 때만 제한. 70% 경고, 85% 진행 중 아카이브 연기, 95% 모든 새 게시 정지. 예약 잔량 구간에서는 최종 회의록만 허용하되 95% 정지 우선. 로컬 자료 삭제 없음. 실시간 게시를 제한하는 운영 선택이므로 승인 후 적용. 집계 기간은 공급자 확인값으로 명시 변경하며 달력 월 변경으로 자동 초기화하지 않음.

## 조회 캐시와 지연

- 공개 성공 GET만 기존 CDN `max-age=1, stale-while-revalidate=2` 유지. 실제 CDN HIT는 이번 시험에서 미측정.
- 변경 API의 읽기는 `useCache:false` 유지. 조회 API도 시간 기반 Blob 캐시를 추가하지 않고 겹치는 읽기만 공유. 별도 함수 인스턴스에는 공유되지 않음.
- 저장소 ETag별 공개 모델은 최대 16개, 항목당 2백만 문자. 직렬화 snapshot은 모델당 최대 8개, 항목당 25만 문자. 새 읽기에서 다른 ETag 확인 시 다시 생성. 큰 응답은 캐시하지 않음.
- 변경 성공·실패 뒤 경로 캐시 무효화. 늦게 끝난 이전 읽기가 이후 새 읽기를 막지 않는 시험 포함. 진행 중이던 이전 요청에는 이전 버전이 도착할 수 있으므로 브라우저도 요청 세대 확인·취소 적용.
- 쿠키·Authorization 포함 요청은 공유 읽기와 CDN 제외. Origin 거부·POST·오류·304는 공유 CDN 제외. gzip;q=0, Content-Encoding, Vary, ETag 검증.
- 채널 목록의 순서·중복은 API 내부 정규화. 브라우저는 선택 채널을 정렬한 URL 사용. 기존 URL을 리다이렉트하지 않으므로 외부 호출자가 만든 URL 조합까지 CDN 키가 같아지는 것은 아님.
- 방송 전환의 broadcast_id 검사, 안정 sequence 커서, 검색과 수정된 회의록 조회 유지. Blob list() 또는 구간별 새 객체 생성 없음.
- 전면 폴링은 기존 5초와 ±20% 지터 유지. 방송 없는 전면 탭도 자동 시작 탐지를 늦추지 않도록 5초 유지. 배경 탭은 조회 중단, 복귀 시 즉시 갱신. 전사 생성 자체의 지연과 영상 30초 지연은 이번 변경 대상 아님.

## 월간 적합성

2026-10-25 [Blob 공식 포함량](https://vercel.com/docs/vercel-blob/usage-and-pricing): Advanced 2,000회, Simple 10,000회, 저장 평균 1GB, Blob 전송 10GB. [Hobby](https://vercel.com/docs/plans/hobby): CDN 요청 100만회. 팀의 기존 소비량·집계 기간·Hobby 사용 목적 적합성은 별도 확인 필요.

하루 8시간, 월 22일, 채널별 10초 변경이 같은 시점에 모이는 가정. 기본 5분 아카이브와 각 묶음의 index 갱신, 최초 snapshot 포함. 실제 청구량이 아닌 계산값.

| 동시 방송 | 월 쓰기 예상 | Advanced 포함량 배수 |
|---|---:|---:|
| 1 | 67,585 | 33.8 |
| 4 | 73,921 | 37.0 |
| 8 | 82,369 | 41.2 |

| 조회자 | 월 브라우저 요청 | CDN 100만회 대비 |
|---|---:|---:|
| 0 | 0 | 게시·Blob 요청 별도 |
| 1 | 126,720 | 0.13배 |
| 50 | 6,336,000 | 6.34배 |
| 300 | 38,016,000 | 38.02배 |

8개 방송 쓰기: 실시간 63,360 + 아카이브 16,896 + index 2,112 + 최초 1. 쓰기가 일정하게 발생하고 기존 사용량이 0인 가정에서 80% 예산 1,600회까지 약 3.42시간, 2,000회까지 약 4.27시간. 날짜 예측이나 계정 초기화일이 아님. 채널 이벤트·아카이브 시점이 흩어지면 더 증가. SDK 추가 시도·운영 변경·다른 프로젝트 사용량도 별도.

조회가 완전히 겹치는 단일 함수 시험의 300:1 읽기 감소를 월 전체에 그대로 적용할 수 없음. 304도 Blob 읽기 이후 판단하므로 본문 0바이트와 원본 요청 0회를 혼동하지 않음. 계산기는 1~37개 선택 조합과 1/4/16개 함수 인스턴스 민감도, 캐시 절감 없는 상한, 재시도·multipart 가정을 별도 출력. 실제 UI 선택은 최대 2개. 8개 전체 텍스트의 벤치마크 바이트는 스트레스 입력이며 실제 UI 월 전송량 예측이 아님.

판정: 유휴 쓰기 낭비를 제거해도 위 실시간 조건과 현재 무료 Blob 구조는 양립 불가. 300명 브라우저 조회만으로도 CDN 포함량 초과. 5분으로 늦추는 조치는 해결책으로 채택하지 않음.

## 대체 구조의 승인 전 비교

| 구조 | 지연·보안 | 운영 부담·한도 | 다음 검증 |
|---|---|---|---|
| 현재 Vercel+Blob | 현재 인증·조건부 쓰기 유지 | 실시간 쓰기·폴링 포함량 초과 | 실제 Usage 확인, 적정 유료 용량 산정 승인 |
| Vercel 정적 화면+기존 PC 공개 읽기 전용 계층+종료 시 아카이브 | 관리자와 분리, TLS·접근 통제·캐시·요청 제한 필수 | PC 전원·회선이 단일 장애 지점, 공개 연결과 운영 승인 필요 | 300명 지속 연결·대역폭·장애 복구 측정 |
| 정적 화면+별도 실시간 상태 서비스+저빈도 아카이브 | 방송별 구독과 수정 이벤트, 재접속 시 커서 복구 | 연결수·전송량·읽기·저장 한도 및 비용을 서비스별 검증해야 함 | 계정·서비스 선정 승인 후 동일 8채널·300명·지연 시험 |

예를 들어 8방송×22일에 방송별 최종 저장 1회이면 아카이브 176회와 목록 갱신 횟수가 추가됨. 이후 재편집·재시도와 실시간 계층 비용은 별도이며 이 산식만으로 무료 운영 보장 불가. 현 `read(path)` / `write(path,value,etag)` 경계와 mock 저장소를 유지해 교체 지점 확보. 신규 연결·터널·DNS·포트 개방·Blob 공개 전환은 미실시.

실행·복구는 [배포 운영 절차](DEPLOYMENT-RUNBOOK.md) 참조.
